# k1s February Update: v0.1.3 Official

`v0.1.3` is now official as of **February 19, 2026**.

This release is guided by the same baseline we just published in `TENETS.md`: digital rights first, consent as a hard requirement, security by default, and decentralization that reduces real control concentration, not just topology concentration. k1s should stay small, understandable, and composable while still being capable in real distributed environments.

That framing only matters if it shows up in defaults and operator workflows. In `v0.1.3`, that means stricter CRI orchestration, clearer ingress policy validation and proof signals, trust-first registry behavior, and a lot of reliability hardening across labs and validation lanes.

## What is now official in v0.1.3

This post reflects the shipped release in `CHANGELOG.md` (`0.1.3 - 2026-02-19`) and the finalized release posture. Compared to v0.1.2 (storage/CRI foundations), v0.1.3 adds major control-plane and data-plane depth for hub/edge deployments with intermittent nodes.

Control plane:
- (Core) NATS/JetStream control channel and durable queue, with Etcd state store SoT
- (Edge) NATS core control channel with local spool, state sync SoT via WG data plane egress tunnel
- strict CRI lane orchestration across core/edge profiles + fail-fast pairing checks
- expanded single-host + multi-site ingress validation matrices (deep/perf)
- richer matrix evidence (lb_policy_passed, lb_strict_proof_passed, lb_observability_passed)
- hardened route-bundle publishing + controller/etcd edge-ingress state alignment

Data plane:
- policy-driven LB + cookie stickiness in core-proxy
- stronger startup/readiness/path-aware/HTTP2 checks across ingress modes
- new site-to-site WireGuard tunnel flow with Rosenpass-managed PSK mode
- overlay visibility now includes WG peer/handshake health + Rosenpass status

Security/testing:
- security baseline + staged active authn/authz test patterns integrated into ingress lanes
- TLS/trust-first registry behavior in strict CRI flows

Why this matters: WireGuard + Rosenpass gives us a practical path to post-quantum-resilient PSK rotation across site-to-site data-plane traffic. 😎

## TL;DR Highlights

- Strict CRI profile orchestration across `k1s-*` lane patterns, including local build fallback and explicit registry/image policy handling.
- Expanded ingress capability validation for CRI with deeper single-host and multisite matrix coverage.

- Benchmarking now captures CRI (`crictl`) container snapshot/inspect data and adds parity assets for k1s vs k3s validation workflows.

## Added (curated)

- Strict CRI profile orchestration for `k1s-core-cri`, `k1s-edge-cri`, `k1s-core-edge-cri`, `k1s-edge-core-cri`, and `edge-site-cri`.
- Ingress capability validation expansion with additional single-host and multisite matrix scenarios plus deeper capability probes.
- Core-proxy ingress controls for LB policy and cookie stickiness.
- Ingress matrix JSON proof surfaces: `lb_policy_passed`, `lb_strict_proof_passed`, `lb_observability_passed`, plus per-row assertion metadata.
- Benchmark workflow capture for CRI via `crictl` snapshot/inspect outputs and new parity benchmark assets.
- New metadata in `pyproject.toml`: `version_codename` set to `Snow Moon`.
- New helper for managed registry trust/bootstrap in strict CRI flows: `scripts/containerd_registry_trust.sh`.

## Changed (curated)

- Runtime profile behavior now auto-detects strict CRI core stacks more explicitly and fails fast on incompatible compose profile pairings.
- Managed registry behavior in CRI profiles now defaults to a TLS/trust-first path, with explicit security-gate guidance for strict runs.
- Ingress validation guidance now uses `core-proxy` as the main policy/observability lane, while strict LB distribution proof remains in `edge-local`.
- Docs server pages, runbooks, examples, and README were refreshed around `k1s-*` profile targets and reproducible strict CRI flows.
- Project messaging in README and Start Here now aligns to TENETS and the current production-validation stance.

## Why this matters

1. Deterministic runtime behavior across mixed home lab, edge, and cloud nodes is mandatory before federation can be trusted.
2. Ingress policy needs proof surfaces, not assumptions; matrix assertions and observability fields make verification concrete.
3. Values only matter when they become defaults. `v0.1.3` pushes privacy/consent/security posture into day-to-day operator paths.

## Technical implications

### Why strict CRI lanes matter

If k1s is going to run across home labs, edge sites, and private cloud nodes, runtime behavior has to stay explicit and deterministic. The strict CRI profile lanes reduce ambiguity when workloads move between core and edge contexts and make failures easier to reason about.

### Why policy proof in ingress matters

A distributed app mesh is only useful when policy behavior is verifiable. The LB assertion and observability fields in matrix outputs provide evidence that routing assumptions actually held during validation, instead of relying on inferred behavior.

## Non-goals (still true)

- k1s is not a Kubernetes clone.
- k1s is not a managed service.
- k1s is not a surveillance or stealth-compute platform.
- No involuntary compute model is acceptable; participation must remain explicit and revocable.

## Deployment readiness

k1s is actively developed and intentionally not at an official MVP state yet. We recommend using this release for controlled staging, lab, and advanced operator validation scenarios while continuing to harden operational paths and failure-mode coverage.

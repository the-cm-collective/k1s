# k1s February Update

Hi all, the project has been evolving rapidly, so I'd like to talk a bit before the update!

What k1s is: "a Python-based, Kubernetes-like app orchestration engine you can actually read and hack on"

The project's philosophy: "Kubernetes-style concepts with a smaller surface area — lightweight deployments, minimal footprint."

I feel pretty good about that for a number of reasons.

For one, "Python" (seriously, who doesn't love Python? *rhetorical question*). Regardless of your personal stance on the language, it has its benefits. It's readable, I feel this makes k1s more approachable to the novice and more hackable to the senpei. Is Python's performance your question? If well architected, Python systems can be optimized for performance. Will there still be shortcoming? Yes, but once I am fully satisfied with the stability and design of the system, I will be able to more accurately identify actual pain points, and explore potential optimization paths. It is not unreasonable that some subsystems and modules may be rewritten in Rust, but Python will remain the primary language of the project.

It's lightweight, it intends to stay that way, while still providing "k8s-like" operation and a level of compatibility. This all started as small project to build a small, k8s style, app engine for resource constrained deployments. At the time, I was pretty entrenched in Kubernetes, running a microk8s cluster in a home lab and GKE professionally. I also thought it would be fun to build a light AE that could run on low cost cloud instances, there was value in it for me on multiple fronts so I pressed on. I've put a lot of focus on memory benchmarks through the early stages of development, in all fairness this is not an apples to apples comparison, but results suggest k1s is substantially lighter than k3s (k3d).

I want it to help engineers and enthusiasts learn how AEs work and pick up some ops patterns along the way. Is it easy to try on your Debian/Ubuntu (MacOS untested, let me know if you try) machine?  Clone the repo, install the deps, and run "make demo". That starts a stack with two example manifests! The next place you want to go is the built in docs server page, assuming you allowed the TLS and hosts entries you will find it running on local host at "https://docs.home.arpa:8443". Give them a read and make your way to the "Playground" and "Dashboard" pages. The playground page provides a guided, interactive, learning flow you can use to exercise the system! You can watch the changes reconcile in the dashboard as you apply them in the playground, fun!

If you want to go a little further, move on to "Concepts in Practice", which is a 10 part series going a little deeper into k1s and app engines in general. I'll be doing a short video series to accompany this, so be sure to subscribe to our YouTube channel and turn on alerts so you get notified when a new episode is released!

Just to wrap things up, we also setup a GitHub org for the project so be sure to watch the project repo for update. That is going to be our primary point for project tracking, issues, etc. If you like k1s or are interested in securing its future, consider sponsoring (anything helps, seriously)!

## v0.1.2 Release (February 4, 2026)

Alright, on to the update. v0.1.2 lands today with a big storage push, CRI runtime work, and more polish in the API shim + dashboard workflow. It is a release that makes k1s more realistic for stateful experiments and a little friendlier for containerd labs.

## TL;DR Highlights

- Storage: CSI-style flows (snapshots, restore/clone, expansion), topology constraints, and volume health signals.
- NetFS/NFS: dynamic NFS provisioning, SELinux-friendly mounts, fsGroup, quotas, and capacity overrides.
- Runtime: CRI/containerd support plus a CRI port-forward proxy path and ingress reload fallback.
- API shim: exec/port-forward foundations, richer OpenAPI metadata, and static Swagger exports.
- CLI + dashboard: namespace targeting, port-forward preview in the UI, and a new shell-demo example.
- Docs + fixes: storage/CRI docs refresh, dashboard visuals update, and a pile of reliability fixes.

## 1) Storage: CSI-Style Flows + NetFS/NFS

Storage is the headline for v0.1.2. We now have CSI-style storage API coverage for snapshots, PVC restore/clone flows, volume expansion, RWOP and multi-attach guardrails, topology constraints, and volume health metrics/events. That means the storage story is finally starting to look like something you can map to real-world workflows instead of a toy example.

On top of that, NetFS/NFS plumbing landed: dynamic NFS provisioning, NetFS mounts with SELinux relabeling + mount options, fsGroup support, storage quotas, block device mappings, and capacity overrides. If you are running a small lab with NFS, this is the first release where that story feels complete.

## 2) CRI Runtime Support (containerd)

We added CRI runtime support and tightened the containerd workflow. CRI is now a first-class runtime backend, and ingress reloads have a fallback path so the system stays recoverable when the underlying reload step flakes.

If you are on containerd and want to experiment, set `AE_RUNTIME_BACKEND=cri`. For port-forward on CRI nodes, there is an optional CRI-native proxy path via `AE_APISHIM_CRI_PORTFORWARD=1`.

## 3) API Shim: Exec/Port-Forward Foundations + Swagger Exports

The API shim got a deeper pass: exec and port-forward foundations are now aligned with the CRI runtime path, plus we added richer OpenAPI examples/metadata and static Swagger export pages. It is still not "full Kubernetes" (and isn't trying to be), but the drift guards and documentation now feel like proper reference material.

## 4) CLI + Dashboard Touches

We added CLI namespace targeting so your app commands can default to a namespace via `--namespace` or `AE_NAMESPACE`. The dashboard now includes a port-forward preview panel in the UI, and the new `shell-demo` example makes it easy to validate the exec/shell workflow end-to-end.

We also refreshed the dashboard visuals and system graph styling with updated background assets. It is a subtle change, but the whole UI feels tighter and more legible.

## 5) Docs + Examples Refresh

Docs and examples have been updated for storage, NetFS, and CRI. That includes ADRs, runbook notes, refreshed README screenshots, and regenerated docs site artifacts. If you rely on the docs site as your front door, this release keeps the story aligned with the features that now exist.

## 6) Reliability Fixes

v0.1.2 also ships a chunk of fixes: local node registration and heartbeat gating are tighter, apishim routing/TLS is hardened (including pod IP preference for port-forward), demo/lab auth bootstrap is more robust, CRI setup + test flows are less flaky in CI, benchmark capture is now isolated by engine, and Labs AIO now honors `AE_RUNTIME_BACKEND`.

If you try it and something feels off, file an issue. Otherwise, enjoy the storage upgrades and let us know how containerd experiments go!

# k1s February Update: v0.1.3 and the Privacy-First Build-out

Hi all, we are preparing the promotion of `v0.1.3` from `dev` to `main` and I wanted to post one note before the formal release callout.

This update is technical, but it is also about context. I care less about hype and more about survivable infrastructure. We all protect our physical spaces because we care about our safety. We should apply the same discipline to our digital spaces. If we are not conscious of what happens to our data, compute, and identity, we quietly hand over leverage to systems we do not control.

We are seeing a world where third-party dependency, narrative capture, and centralized control can drift from convenience into coercion. We do not need another platform that asks for obedience in exchange for convenience. We need systems where each participant keeps agency, can verify behavior, and can leave when policy changes. A distributed model is a first line of defense: not only technical redundancy, but also political and social resilience.

I am a cloud architect by trade and, to be blunt, a hacker at heart. I keep asking the same question: how do we give people real compute back as a public resource without turning participation into a botnet? My answer in K1S is still evolving, but it is clear now: build software that is readable, permissioned, and composable, then make community compute the default path.

## Why this release matters now

The project started as a small, practical need: a lightweight, Kubernetes-like engine for reproducible deployment and control. I wanted something with a small footprint, predictable behavior, and room to learn in public.

Today, with home clusters, edge devices, RPi stacks, and home labs everywhere, we now have enough idle capacity to treat compute as a distributed common good. The hard part is not the hardware. The hard part is the fabric.

We now have options, but most people cannot stitch them together safely. Too many choices mean too much operational risk.

So this release is important because it lowers that complexity barrier for practical, consent-aware, federated compute.

## What v0.1.3 delivers

`v0.1.3` is the first release focused on production-grade federated behavior under constrained and transient environments. It is also the release where we start saying out loud the direction this project is taking: privacy/security first and distributed control over centralized surrender.

## Added

- Strict CRI profile orchestration for multiple lane patterns, including `k1s-core-cri`, `k1s-edge-cri`, `k1s-core-edge-cri`, `k1s-edge-core-cri`, and `edge-site-cri`, with registry mode, image policy, and local build fallback handling.
- Expanded CRI ingress capability validation with single-host and multi-site matrices, stronger probes, and a stricter performance-oriented validation harness.
- Core-proxy ingress policy controls for load balancing and cookie stickiness.
- Ingress matrix output now includes assertion and observability metadata for LB policy checks.
- Benchmark capture now includes CRI `crictl` container snapshot and inspect data through rollout/matrix workflows.
- Added a project `version_codename` (`Snow Moon`) metadata entry.

## Changed

- Docs and README guidance was refreshed around CRI profiles and strict validation flows, including examples for classic and strict CRI paths.
- Ingress deep validation now treats `core-proxy` as the main policy and observability lane, with strict LB distribution proof kept in the `edge-local` path.
- Runtime behavior now auto-detects strict CRI core stacks more explicitly and fails fast on incompatible compose profile pairings.
- Benchmark docs and charts now carry CRI scenario annotations and reproducible execution context.

## Fixed

- Route bundle publishing and controller/etcd edge-ingress state handling were hardened.
- Core-proxy startup and readiness checks improved for better reliability.
- CRI strict mode sequencing and multi-site reproducibility were stabilized.
- Demo and lab reliability fixes, including log streaming behavior, stale path cleanup, Caddy reload behavior, and cleaner reset behavior across environments.
- Auth and state export paths now align more consistently so CLI status better reflects controller state.

## Technical implications

### 1) Why the CRI lane work matters

If K1S is to run across homes, labs, and private clouds, runtime compatibility must be explicit and deterministic. The new strict profiles reduce ambiguity when workloads move between core and edge contexts. This is what we need before you can trust distributed control instead of a brittle demo.

### 2) Why core-proxy controls matter

A distributed app mesh is only useful when you can prove policy behavior. The LB and observability metadata additions are intentionally boring from a marketing perspective, but they are critical for trust: they let operators see whether policy assumptions held and whether observability evidence exists.

### 3) Why the release is not just engineering

This is where our project values come in.

- **Digital rights first.** Privacy is not a feature line item, it is the default behavior.
- **Consent is non-negotiable.** Shared compute must be explicit and revocable.
- **Security by default.** Small systems are still exploitable systems unless defaults are hard-wired.
- **Decentralize power, not just topology.** Federation is not just more nodes, it is less single-point control.

These principles are what make the difference between a useful tool and another platform that eventually harvests attention or resources without accountability.

## A note on non-goals

K1S is still not a managed service and not a Kubernetes clone. It is also not a surveillance platform and not a stealth compute protocol. There are no hidden compute obligations in this model. If there is no clear opt-in and no auditable policy, it is the wrong design.

## Deployment Readiness

K1S is actively developed and intentionally not yet at an official MVP state. We are still actively testing ops patterns, running workload validation suites, and preparing a staging candidate that is entering continuous test cycles. Until then, we do not recommend deploying `main` or `dev` in public production environments unless you are deeply familiar with running compute clusters and fully understand the operational and security implications.

## What I am asking for

If you have spare compute capacity, please help with operations and security testing in your own environment. If you run home servers, cloud VMs, or hobby clusters, this is the right time to validate single-host or multi-host setups.

For most advanced users, the `multinode-lab` docs server page should be enough to get started quickly with test environments.

Please start operational or security testing conversations in GitHub issues so we can coordinate and follow up directly.

## Final thought

You can still call this project a small app engine. I still call it a small engine. But the question is no longer whether it is small. The question is whether it is ours.

We can no longer afford to let convenience become blind trust. As siblings, as parents, as friends, as people, we either participate in systems that take our choices, or we build systems where participation is explicit, revocable, and accountable.
